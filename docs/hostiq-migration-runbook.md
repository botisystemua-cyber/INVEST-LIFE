# Перенесення сайту + домену на HOSTiQ — бойовий ранбук (стартовий промт)

Документ описує повний цикл переїзду WordPress-сайту з чужого хостингу на HOSTiQ,
включно зі зміною DNS, SSL і редіректом. Придатний як стартовий контекст для агента.

Складено за реальним кейсом: `investlife.com.ua`, ADM.tools → HOSTiQ (акаунт HQ20),
серпень–вересень 2026. Усі граблі в §9 — справжні, кожна коштувала часу.

> **Головний урок кейсу:** хостер переніс файли, але **не переніс базу**. Сайт
> запрацював і виглядав робочим, бо `wp-config.php` далі вказував на MySQL старого
> хостингу. Виявилось це лише через діагностику 19-секундного TTFB. Якби не помітили —
> сайт ліг би намертво в день закриття старого акаунта.
> **Перевіряй `DB_HOST` одразу після переносу. Це перша дія, не остання.**

## 0. Порядок дій (велика картина)

| # | Крок | Хто робить | Час |
|---|------|-----------|-----|
| 1 | Зібрати доступи (FTP, MySQL, панель) | ти | 20 хв |
| 2 | Заявка на безкоштовний переїзд | ти → HOSTiQ | 5 хв |
| 3 | Перенесення файлів + БД | HOSTiQ | години–доба |
| 4 | **Перевірка `DB_HOST`** ⚠️ | ти | 2 хв |
| 5 | Перевірка сайту через `hosts` (до зміни DNS) | ти | 15 хв |
| 6 | Вимкнути DNSSEC (якщо ввімкнено) | ти, у реєстратора | 2 хв |
| 7 | Зміна NS | ти, у реєстратора | 5 хв |
| 8 | Очікування розповсюдження DNS | — | 1–24 год |
| 9 | Випуск SSL (Let's Encrypt) | HOSTiQ / AutoSSL | 15 хв |
| 10 | Редірект / фінальні налаштування | ти | 15 хв |
| 11 | Трансфер домену (опційно, окремо) | HOSTiQ | дні |

**Критично:** кроки 7 і 11 — РІЗНІ речі. Зміна NS перемикає, куди вказує домен

роботи сайту достатньо NS.** Не роби обидва одночасно — не зрозумієш, що зламалось.

```

MySQL:
  Хост, назва бази, логін, пароль, розмір і кількість таблиць
```

Паролі FTP/MySQL зазвичай невідомі (акаунт клієнта) — перевстанови їх у панелі
донора. Це безпечно, сайт від цього не падає. **Після переїзду зміни ще раз** —
вони пройшли через переписку з підтримкою.

## 2. Заявка в HOSTiQ

У них **безкоштовне перенесення**, але тікет у підтримку — не той канал.
Треба заповнити форму: `https://hostiq.ua/ukr/transfer-form/`

Форма просить **доступ до панелі керування** старого хостингу, не FTP.

**Якщо на панелі донора двофакторка** (а вона часто є, і коди йдуть на пошту
власника) — не знімай захист із чужого акаунта. Замість цього:

1. Дай FTP-доступ до файлів
2. Зроби дамп бази і поклади його **на той самий FTP**
3. Напиши, що панель недоступна, але є файли + дамп

HOSTiQ на таке погоджуються самі.

⚠️ **Дамп клади ВИЩЕ кореня сайту** (`/home/user/`, не `/home/user/www/`).
У веб-папці його зможе скачати будь-хто, вгадавши адресу. Там уся база клієнтів.

### Питання, які варто поставити одразу

```
1. Чи вистачає ліміту тарифу на ще один сайт?
2. Які NS прописати для домену?
3. Чи буде перенесена база даних, і з якими реквізитами?  ← НЕ ЗАБУВАЙ
```

Третє питання — прямий наслідок головних граблів цього кейсу.

## 3. Перевірка ПІСЛЯ переносу (найважливіший розділ)

### 3.1 DB_HOST — перша дія

cPanel → Диспетчер файлів → папка сайту → `wp-config.php` → «Редагувати» → Ctrl+F `DB_HOST`

```php
define( 'DB_HOST', 'localhost' );          // ✅ добре
define( 'DB_HOST', 'ce625858.mysql.tools' ); // ❌ база НЕ перенесена
```

Якщо там хост донора — сайт працює через інтернет із чужою базою. Симптоми:
повільно, і **гарантована смерть** у день закриття старого акаунта. Пиши хостеру
негайно, це їхня недоробка в межах безкоштовного переїзду.

### 3.2 Діагностика повільного сайту

Три заміри розділяють причини:

```bash
# Статика — якщо швидко, сервер і мережа в порядку
curl -sS -o /dev/null -w "CSS: %{time_total}s\n" https://site.com/wp-content/themes/x/style.css

# Найлегша PHP-сторінка — якщо повільно, гальмує СТАРТ WordPress
curl -sS -o /dev/null -w "login: %{time_starttransfer}s\n" https://site.com/wp-login.php

# Блокується до запуску PHP — контрольна точка
curl -sS -o /dev/null -w "xmlrpc: %{time_starttransfer}s\n" https://site.com/xmlrpc.php
```

**Читання результатів:**

| Картина | Причина |
|---|---|
| статика швидко, будь-який PHP однаково повільно | віддалена БД або очікування таймауту |
| повільна лише головна | важкий контент, кеш, плагіни рендерингу |
| усе повільно, включно зі статикою | сервер перевантажений |

### 3.3 Пошук винуватця серед плагінів

Не перебирай по одному. Перейменуй **усю папку** `wp-content/plugins` → `plugins.off`,
зміряй, поверни назву.

- Швидко стало → винен плагін, далі ділиш список навпіл
- Не змінилось → плагіни ні до чого, копай глибше

⚠️ **Під час тесту не заходь у `/wp-admin`.** Якщо WordPress завантажить адмінку і
не знайде плагінів — позначить їх вимкненими в базі, і доведеться вмикати руками.
Поки адмінку не чіпаєш, статус у базі не міняється.

### 3.4 Шукати також

```
wp-content/object-cache.php     — drop-in Redis/Memcached від старого хостингу
wp-content/advanced-cache.php   — те саме для сторінкового кешу
wp-config.php: WP_REDIS_*, MEMCACHED_*, WP_CACHE_KEY_SALT
```

Якщо старий хостинг мав Redis, а новий ні — WordPress чекає таймаут на кожному
запиті. Лікується перейменуванням файлу.

## 4. Перевірка сайту ДО зміни DNS (файл hosts)

Дозволяє подивитись сайт на новому сервері, поки домен ще вказує на старий.

**Windows:**
```
C:\Windows\System32\drivers\etc\hosts
```

Блокнот **від імені адміністратора** → Файл → Відкрити → тип «Усі файли» → шлях вище.

Додати:
```
45.83.192.189 site.com
45.83.192.189 www.site.com
```

Кодування **ANSI**, без розширення, Ctrl+S має пройти **без діалогів**.

Швидше через PowerShell від адміністратора:
```powershell
Add-Content -Path "$env:WinDir\System32\drivers\etc\hosts" -Value "`n45.83.192.189 site.com`n45.83.192.189 www.site.com"
ipconfig /flushdns
```

Перевірка: `ping site.com` має відповісти новим IP.

**З боку агента** те саме робиться без hosts:
```bash
curl -sS --resolve site.com:443:45.83.192.189 https://site.com/ -k -o page.html
```

Або рендер зі скриншотом (Playwright + Chromium):
```js
chromium.launch({
  executablePath: '/opt/pw-browsers/chromium',
  args: ['--no-proxy-server', '--host-resolver-rules=MAP site.com 45.83.192.189'],
})
// context: { ignoreHTTPSErrors: true }  ← сертифікат ще тимчасовий
```

⚠️ **Видали рядки з hosts одразу після перевірки.** Інакше твій комп'ютер назавжди
ходитиме на цей IP, і ти не побачиш реального стану сайту.

## 5. Зміна NS

### Спершу — DNSSEC

Якщо DNSSEC увімкнено, а NS змінились — домен перестане резолвитись **повністю**.
Вимикай за добу до зміни. Перевір у панелі реєстратора.

### Зміна

Панель реєстратора → домен → «Нейм-сервери (NS)» → замінити на NS хостера.
HOSTiQ: `dns1.hostiq.ua`, `dns2.hostiq.ua`. Зайві поля очистити.

### Якщо реєстратор відмовляє

```
Не вдалося змінити NS. Перш ніж змінювати сервер DNS, необхідно
налаштувати домен на сервері dns1.hostiq.ua
```

Реєстратор перевіряє, чи новий NS уже знає про домен. Дії:

1. Попросити хостера **створити DNS-зону** для домену
2. Спробувати ще раз
3. Якщо знову — поставити галочку «Не перевіряти наявність домену на вказаних NS»

Галочка безпечна, **якщо хостер письмово підтвердив, що зона створена**. Відкат —
повернути старі NS, дві хвилини.

### Після зміни

`.com.ua` — офіційно 8–24 год, фактично зазвичай 1–4.

```bash
python3 -c "import socket;print(socket.gethostbyname('site.com'))"
```

## 6. SSL

**Порядок жорсткий:** спершу DNS, потім сертифікат. Let's Encrypt перевіряє право на
домен через HTTP-запит до нього — поки DNS вказує на старий сервер, випуск неможливий.

Доти на новому сервері стоїть самопідписаний сертифікат. У браузері:
`ERR_CERT_AUTHORITY_INVALID`. **Це нормально на цьому етапі**, не поломка.

Обійти для перевірки: «Розширені» → «Перейти (небезпечно)», або набрати на сторінці
помилки `thisisunsafe` (Chrome слухає приховано).

Після перемикання DNS: cPanel → **SSL/TLS Status** → обрати домен і `www` → **Run AutoSSL**.
Не спрацювало — тікет хостеру, роблять за хвилини.

⚠️ Перевірити сертифікат із-під агента **не вийде**, якщо середовище проксює TLS —
побачиш сертифікат проксі, а не справжній. Це перевіряє людина в браузері.

## 7. Редірект на інший сайт

`.htaccess` у корені, **на самому початку файлу**:

```apache
# --- Редірект на інший сайт ---
RewriteEngine On

RewriteCond %{REQUEST_URI} !^/wp-admin
RewriteCond %{REQUEST_URI} !^/wp-login\.php
RewriteCond %{REQUEST_URI} !^/wp-content
RewriteCond %{REQUEST_URI} !^/wp-includes
RewriteCond %{REQUEST_URI} !^/\.well-known

RewriteRule ^(.*)$ https://target.com/?ref=marker [R=302,L,QSA]
```

| Елемент | Навіщо |
|---|---|
| `!^/\.well-known` | **КРИТИЧНО.** Через цей шлях Let's Encrypt поновлює сертифікат. Без винятку SSL помре через 90 днів |
| `!^/wp-admin`, `!^/wp-login\.php` | інакше втратиш доступ до адмінки |
| `R=302` | тимчасовий. 301 браузери кешують намертво — передумаєш, а в людей редірект житиме місяцями. Ставити 301 лише коли впевнений |
| `QSA` | доносить UTM-мітки з реклами до цільового сайту |
| `?ref=marker` | мітка джерела в аналітиці приймача |

**UTM ставити на боці реклами, не в редіректі.** Інакше конфлікт із мітками кампанії:
```
https://site.com/?utm_source=google&utm_medium=cpc&utm_campaign=xxx
→ https://target.com/?ref=marker&utm_source=google&utm_medium=cpc&utm_campaign=xxx
```

Якщо на домені лежить скрипт (вебхук, API-приймач) — додай і йому виняток:
```apache
RewriteCond %{REQUEST_URI} !^/capi\.php
```

### Перевірка редіректу

LiteSpeed віддає кешовані сторінки і показує старий вміст. Тестуй так:

```bash
# в обхід кешу
curl -sS -o /dev/null -w "%{http_code} -> %{redirect_url}\n" -H "Cache-Control: no-cache" https://site.com/

# неіснуюча сторінка — точно не в кеші
curl -sS -o /dev/null -w "%{http_code} -> %{redirect_url}\n" https://site.com/zzz-test-$RANDOM/

# UTM доїжджають?
curl -sS -o /dev/null -w "%{redirect_url}\n" -H "Cache-Control: no-cache" \
  "https://site.com/?utm_source=google&utm_medium=cpc"

# адмінка не зламалась?
curl -sS -o /dev/null -w "%{http_code} %{redirect_url}\n" https://site.com/wp-login.php
```

Після правок: wp-admin → LiteSpeed Cache → Toolbox → **Purge All**.

## 9. Граблі (всі реальні)

**База не перенесена, а сайт працює.** Головні граблі кейсу. `wp-config.php` вказував
на MySQL донора, сайт віддавав перший байт за 19 с. Перевіряй `DB_HOST` першим ділом.

**Симптом віддаленої БД:** вимкнення всіх плагінів прискорює сайт у 8 разів — але
винні не плагіни, а кількість SQL-запитів, кожен з яких іде через інтернет. Легко
піти хибним слідом і перебирати плагіни годинами.

**Хостер читає запит навпаки.** На «приберіть залишки Redis від старого хостингу»
прийшла відповідь «Redis на віртуальному хостингу недоступний, потрібен VPS».
Формулюй прямо: «прошу **видалити** налаштування X», з замірами як доказом.

**Перша лінія підтримки не має доступу.** Технічні речі — на `tech@hostiq.ua` або
тікетом із Панелі клієнта. У чаті вирішують прості задачі.

**Support PIN** у листі економить цикл верифікації. Якщо пишеш не з реєстраційної
пошти акаунта — вкажи і номер акаунта, і PIN, і реєстраційну адресу.

**Крапка в кінці адреси.** `site.com.` і `site.com` — різні хости для браузера.
Запис у `hosts` не спрацює, сертифікат не збігається, CSS блокується, сторінка
виглядає «голою». Легко не помітити в адресному рядку.

**Браузери не вміють FTP.** Chrome і Edge викинули підтримку. `ftp://` посилання
вони відправляють у пошук або пропонують відкрити інший браузер. Тільки Провідник
Windows (Win+E) або FileZilla.

**`@` у паролі ламає FTP-посилання.** У `ftp://user:pass@host` символ `@` розділяє
пароль і хост. Пароль із `@` робить готове посилання від хостера непрацездатним.
Вводь логін/пароль окремими полями.

**Блокнот без прав адміністратора** не збереже `hosts` — мовчки запропонує зберегти
в Документи або допише `.txt`. Ознака успіху: Ctrl+S не показує жодного вікна.

**LiteSpeed маскує зміни.** Після правок `.htaccess` сайт може віддавати старий
вміст. Перевіряй із `Cache-Control: no-cache` або на неіснуючій сторінці.

**Різниця між NS і трансфером.** Клієнт каже «перенеси домен», маючи на увазі «хай
сайт працює». Це зміна NS — безкоштовно і за години. Трансфер реєстратора — окрема
платна процедура, і для роботи сайту не потрібна.

**PHP не лікує таймаути.** Оновлення 7.4 → 8.2 дає 20–30% на генерації сторінки.
Якщо сайт висить 14 секунд — це очікування чогось, і версія PHP тут ні до чого.

## 10. Чеклист перед «готово»

```
[ ] DB_HOST = localhost, база на новому сервері
[ ] TTFB < 3 с на головній і на /wp-login.php
[ ] Домен резолвиться в IP нового хостингу (site.com і www)
[ ] SSL валідний, замочок у браузері без попереджень
[ ] HTTP → HTTPS редірект працює
[ ] Внутрішні сторінки відкриваються (ЧПУ і .htaccess цілі)
[ ] /wp-admin доступна
[ ] Форми зворотного зв'язку працюють, заявки доходять
[ ] .well-known виключено з редіректу
[ ] Рядки з hosts видалено
[ ] Паролі FTP/MySQL змінено після переїзду
[ ] Резервна копія .htaccess збережена
[ ] Заявки за період міграції звірено (писались у стару базу)
[ ] Старий хостинг ще живий як страховка
```
